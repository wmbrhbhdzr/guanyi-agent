# 实验6 设计增量：工具调用、单 Agent 与运行时 Harness

> 实验3 的架构基线（分层 + 端口适配器、`core` 无出边）保持不变。
> 实验6 新增一个**运行时包 `guanyi/agent/`**：它不修改业务层，而是把已有的数据层与知识层
> 包装成**受控工具**，再用 Harness 把“模型决策 → 工具执行 → 结果回传”的循环跑起来。

## 一、新增能力与模块

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `guanyi/agent/protocol.py` | 工具 Schema 定义、参数校验、**白名单**、路径锚定；`ToolError` 统一错误码 | 标准库 |
| `guanyi/agent/tools.py` | 5 个工具的实现：`list_runs`、`get_decisions`、`compute_stats`、`query_knowledge`、`write_report` | `data`（JsonlStore/SessionService）、`knowledge`（Retriever） |
| `guanyi/agent/harness.py` | 运行时循环：模型调用、工具分发、结果回传、停止控制、成功校验 | `ai`（LlmClient）、protocol、tools |
| `guanyi/agent/runtime.py` | 守护线程有界等待，到期停止等待，允许后台操作继续结束 | 标准库 |
| `guanyi/agent/confirm.py` | 人工确认：CLI（y/N + 超时拒绝）、GUI（弹窗 + 倒计时）、自动同意/拒绝桩 | 标准库 / tkinter |
| `guanyi/agent/trace.py` | 运行记录：任务编号、事件 JSONL + 人类可读日志、密钥遮挡 | 标准库 |
| `guanyi/cli.py` 新增 `agent` | 命令行入口：`--task/--max-steps/--timeout/--yes/--tools` | agent |
| `guanyi/ui/main_window.py` 新增「复盘 Agent」页 | 任务输入、实时日志、确认弹窗、最终结论 | agent |

## 二、数据流（对应报告图 3 的循环）

```
任务目标（自然语言）
  → Harness 初始化（任务编号 / 限制 / 日志 / 工具白名单）
  → [循环] ① 停止检查（步数、总时限）
           ② 模型调用（附带 tools Schema，deepseek-flash 原生 tool_calls）
           ③ 有工具调用？── 否 → 最终回答 → 程序侧成功校验 → 结束
                │是
                ├ ④ 白名单 + 参数校验（失败 → 错误回传，模型可有限次修正）
                ├ ⑤ 写操作？→ 人工确认（拒绝/超时 → 不执行，回传“未确认”）
                ├ ⑥ 执行工具（带超时）→ 结构化结果或错误
                └ ⑦ 结果以 role=tool 写回上下文 → 回到 ①
```

## 三、与实验3/4/5 的衔接

| 实验3 的设计要素 | 实验6 的落地 |
| --- | --- |
| 分层（ui/cli → app → core → data） | agent 作为**运行时外壳**位于最外层，只调用 `data`/`knowledge` 的公开方法，不触碰 `core` 内部 |
| 接口 I-5 记录 / I-6 报告 | 通过工具 `compute_stats` / `write_report` 暴露，写操作需确认 |
| 真值隔离（决策只读画面） | 本实验为离线复盘：`get_decisions`会把历史局面摘要传入复盘模型；这不等于在线视觉决策。历史记录不得作为在线决策模型的输入，也未接入游戏执行通道 |
| 实验4 的异常与日志 | 工具错误统一 `ToolError`；运行记录按任务号落地 |
| 实验5 的知识检索 | `query_knowledge` 把 `Retriever.search` 暴露给模型，作为“解释依据”工具 |

## 四、权限边界（由程序执行，不写在提示词里）

| 类别 | 内容 |
| --- | --- |
| 允许自动执行 | `list_runs`、`get_decisions`、`compute_stats`、`query_knowledge`（全部只读） |
| 必须人工确认 | `write_report`（覆盖写 `data/runs/<run_id>/report.md`） |
| 文件范围 | 读取 `data/runs` 和 `knowledge`；经确认覆盖写目标 `report.md`，日志写入 `data/agent`；业务层同时保留既有 `data/runs/.../app.log` |
| 明确禁止 | 访问声明范围外的文件、执行游戏动作注入、按模型给出的名字动态执行函数/命令、读取游戏进程内存 |

## 五、验收条件

| 用户故事 / 需求 | 本实验的满足方式 |
| --- | --- |
| US-01 看到建议与理由、理解“为什么” | Agent 结论包含统计数字与知识库依据（`query_knowledge`） |
| US-02 逐回合复盘 | `get_decisions` + `write_report`（报告写入需确认） |
| 2.5 失败处理与可观测性 | 参数错误/工具异常/超时/步数上限都有明确状态；运行记录可复核 |
| 2.6 测试与结果分析 | 当前27个Agent单测，合计51个；正常流程保留历史真实模型运行，旧图对应当时的13/37个用例 |

## 六、已知局限

- 单 Agent，无多 Agent 协作；工具只有 5 个，未覆盖截图识别与动作执行（那是实验3 的 `exec` 适配层，本实验不接）；
- 成功校验是“数字与工具结果一致 + 必备字段齐全”的规则校验，不是语义级判断；
- 人工确认在 GUI 里是阻塞式弹窗（倒计时 30 秒），CLI 里是线程读输入 + 超时；
- 超时只是**停止等待**，后台并不存在可强制中断的远程调用，这一点在报告 3.5 节说明。

2026-11-03补充：`runtime.wait_call`执行有界等待，`LlmClient`的退避重试遵守截止时间；
确认使用剩余预算，GUI仍在主线程处理倒计时。写入状态不明则停止并锁住本进程同一数据目录的后续写入，退出后核对文件再决定重试。
成功校验按字段比较数值、完整回合集合与目标对局，报告检查存在及SHA-256；仍不负责证明整段自然语言推理正确。
