# 实验6 AI 辅助编码协作记录

> 记录实验6 里 AI 初稿 → 运行暴露 → 人工判断 → 修正 → 测试通过的完整链条，并给出四类代码审查结论。
> 与实验4/5 相同：AI 负责按设计落地代码，本人负责定任务边界、跑真实模型、核对日志与截图。
> 前六个案例为2026-10-27的历史记录；2026-11-03新增复核见第五节。

## 一、协作原则

- **限制类需求由程序实现**：白名单、参数校验、步数/时限、人工确认、成功校验都写成代码并配测试，
  不写成提示词里的“请不要……”；
- **真实流程必须真跑**：正常完成用真实 `deepseek-flash` + 真实工具跑一次（不是夹具）；
- **错误方案如实记录**：本轮共发现并修正 6 处问题，其中 3 处是 AI 初稿的实质缺陷。

## 二、修正链条

### 案例 1　`Trace.close()` 签名不一致（运行即崩）

- **AI 初稿**：`Trace.close(status, extra=None)`，而 Harness 里按 `close(status, steps=..., elapsed_ms=...)` 调用。
- **暴露**：第一次真实运行走到“结束任务”就抛 `TypeError: close() got an unexpected keyword argument 'steps'`。
- **人工判断**：这是运行记录收尾逻辑，属于必须修的实现缺陷，不是调用方写错。
- **修正**：`close(status, **extra)`，把 step/耗时/工具序列统一塞进 `run_end` 事件。
- **验证**：真实运行成功（4 步、10,054 ms），`data/agent/task-*.jsonl` 的 `run_end` 事件字段齐全。

### 案例 2　密钥遮挡正则误伤任务号

- **AI 初稿**：`SECRET_PATTERN = r"sk-[A-Za-z0-9_\-]{6,}"`。
- **暴露**：查看运行日志时发现任务号显示成 `task-***`（`ta**sk-**20261027…` 被当作密钥片段）。
- **人工判断**：任务号是可观测性的关键字段，必须完整；遮挡只应对真正的密钥生效。
- **修正**：加负向断言 `(?<![A-Za-z0-9])sk-[...]`；复测：任务号完整、`sk-abcdef…` 仍被遮成 `sk-***`。

### 案例 3　“资料不足”被当成工具错误

- **AI 初稿**：`query_knowledge` 在检索无结果时返回 `{"ok": false, ...}`。
- **问题**：Harness 把 `ok=false` 计为**工具错误**，两次无关问题就会触发“连续错误上限”而提前结束任务，
  而这其实是**有效结果**（知识库确实没有）。
- **修正**：改为 `{"ok": true, "insufficient": true, ...}`，不计入错误，模型可自行换问法或跳过。
- **验证**：`test_tools.py` 中该用例从 `FAIL` 变为 `OK（资料不足，有效结果）`。

### 案例 4　改 CLI 时误删了两处代码

- **过程**：为加入 `agent` 子命令，用文本替换编辑 `cli.py`，一次替换误删了 `cmd_context` 的文档字符串、
  另一次误删了 `_add_state_args` 里的 `--hp/--max-hp/--energy` 三个参数。
- **暴露**：立刻用 `python -m guanyi.cli --help` 与单元测试发现（`record` 命令少了参数）。
- **修正**：按原样补回，并跑 `--help` + 37 个单测确认无回归。
- **教训**：文本编辑要缩小替换范围、改完立刻跑一次入口自检。

### 案例 5　循环图排版返工两次

- **AI 初稿**：一版方框宽度不足导致文字溢出，且使用了 `⑪⑫`（微软雅黑缺字形，显示成 `□`），
  右侧分支框互相重叠。
- **人工判断**：报告要求“循环图”，图必须清晰可读。
- **修正**：改为三列布局（主流程 / 左侧分支 / 右侧终点），精简箱内文案，`11./12.` 代替缺字形，
  重跑绘图脚本并目视检查通过。

### 案例 6　UI 冒烟里 Agent 校验失败（夹具问题）

- **现象**：界面冒烟测试中 Agent 状态为 `validation_failed（compute_stats_called 未通过）`。
- **定位**：冒烟用临时数据目录，里面没有 `run-0001`，工具返回 `not_found`，成功校验自然不过。
- **修正**：冒烟脚本先 `seed_sample_run` 准备数据，并让假结论的数字与样例一致 → 校验通过。

## 三、代码审查（讲义要求四类检查）

| 检查项 | 方法 | 结论 |
| --- | --- | --- |
| 不存在的接口 | `importlib` 导入全部模块 + `compileall` | 通过；`agent` 包与 `cli`/`ui`/`qa_service` 引用一致 |
| 无用依赖 | 扫描 `guanyi/agent`、`tests`、`scripts` 的 import | 只用标准库（json/re/dataclasses/threading/queue/tkinter），未引入 agent 框架 |
| 遗漏的异常处理 | 对照五类场景逐项检查 | 工具内部异常→`tool_failed`；参数/JSON→`invalid_*`；确认拒绝/超时→`not_confirmed`；模型失败/超时→`model_error`/`timeout`；均有明确状态 |
| 明显安全问题 | 检查白名单、路径、密钥、写操作 | 不按模型给的函数名执行；run_id 正则 + 存储层拼路径；密钥不打印且日志遮挡；写操作必须确认；运行记录不含个人信息 |

## 四、结论

1. 本实验最容易出问题的是**运行时细节**（收尾、计数、错误分类、日志字段），而不是算法——
   所以“先真跑一次”比“先读代码”更快暴露问题。
2. AI 可以放心交付：工具 Schema、循环骨架、测试夹具、绘图脚本；
   必须人工把关：错误分类口径（资料不足≠错误）、日志字段可用性、确认流程、任务边界。
3. 已知局限：成功校验为规则级；超时无法强制中断远端调用；单 Agent、无多步规划的记忆。
