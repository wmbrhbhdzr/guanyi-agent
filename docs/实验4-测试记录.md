## 一、初版结果汇总（v0.1：5 失败 / 1 未覆盖）

| # | 用例 | 类型 | 初版结果 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | 查询不存在的对局 | 数据不存在 | `FileNotFoundError: data\runs\run-9999\run.json`（裸异常、英文栈） | ✗ 失败 |
| 2 | `decisions.jsonl` 混入损坏行 | 格式错误 | `json.decoder.JSONDecodeError: Expecting property name ...`（裸异常） | ✗ 失败 |

> 初版只做到“骨架 + 能跑通一次数据读写 + 一个操作入口”，因此**没有输入校验、没有去重、

## 二、修复内容与复测结果（v0.2）

| # | 用例 | 修复内容 | 修订版复测结果 |
| --- | --- | --- | --- |
| 1 | 查询不存在的对局 | `JsonlStore.load_run()` 先判断文件是否存在，不存在抛 `NotFoundError(code=not_found)`；命令行统一捕获 `GuanyiError`，打印中文提示并返回退出码 2 | ✅ `{"ok": false, "error": {"code": "not_found", ...}, "zh": "找不到这条记录，可能已被清理"}`，`exit=2` |
| 2 | 记录文件被损坏 | 新增 `scan_decisions()`：逐行解析，损坏行跳过并在 `problems` 里给出行号与原因；`load_decisions(strict=True)` 保留严格模式 | ✅ `{"ok": true, "decision_count": 3, "problems": [{"line": 4, "error": "JSONDecodeError", ...}]}`，`exit=0`；严格模式抛 `StorageError` |
| 3 | 同一回合重复录入 | `SessionService.record_decision()` 落盘前检查 `(run_id, turn)` 是否已存在，重复抛 `DuplicateError(code=duplicate_record)` | ✅ `{"ok": false, "error": {"code": "duplicate_record", ...}}`，记录数仍为 3，`exit=2` |
| 4 | 置信度取值越界 | 领域对象新增 `DecisionPoint.validate()`：`confidence` 必须 ∈ [0,1]，落盘前统一校验 | ✅ `{"ok": false, "error": {"code": "invalid_input", "message": "置信度必须在 0–1 之间", ...}}`，`exit=2` |
| 5 | 动作类型非法 | 新增 `validate_action()`：`action_type` 必须是 `play_card／end_turn／use_potion` | ✅ `{"ok": false, "error": {"code": "invalid_input", "message": "...只能是 play_card／end_turn／use_potion"}}`，`exit=2` |
| 6 | 空对局生成报告 | 新增 `cli start` 入口与 `seed_empty_run()`；报告生成对“0 个决策点”单独处理 | ✅ `{"ok": true, "summary": {"decision_count": 0}, "path": "data/runs/run-empty/report.md"}`；报告正文写明“本局**没有决策点记录**” |

## 三、自动化测试

把上述用例固化为标准库 `unittest`（不引入新依赖），另补 4 个用例覆盖核心闭环：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

| 用例 | 覆盖点 |
| --- | --- |
| 1 数据不存在 | `NotFoundError` |
| 2 格式错误 | 损坏行容错 + 行号报告 + 严格模式 |
| 3 数据冲突 | 重复 `(run_id, turn)` 被拒 |
| 4 无效输入（越界） | `confidence ∈ [0,1]` |
| 5 无效输入（枚举） | `action_type` 白名单 |
| 6 空数据 | 空对局报告 |
| 7 核心闭环 | 规则基线决策 → 护栏 allow → 落盘 → 报告 |
| 7b 规则基线保血分支 | 意图 ≥ 血量 1/3 时先出防御 |
| 8 护栏拦截 | 建议不在合法动作集 → `deny` + `guardrail_trigger` + 留痕 |
| 9 报告内容 | 逐回合表、关键决策点、一致率 |
| 10 日志 | `app.log` 记录录入与护栏拦截 |

**测试结果：`Ran 11 tests ... OK`**（11/11 通过）。

> 过程中有一处值得记录的修正：用例 7 最初的断言写成“血量 42、意图 11 时应建议防御”，
> 运行后失败——按规则“意图 ≥ 当前血量三分之一才保血”，42 的三分之一是 14，11 点攻击
> 不触发保血，**基线出“打击”才是正确的**。因此修正断言，并补充用例 7b 专门覆盖保血分支。
> 这说明：先跑测试再改代码，能避免“把实现改成迎合错误预期”。
