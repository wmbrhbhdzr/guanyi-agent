## 二、通用规范（12 张都适用）

1. **白底无网格、无阴影**。draw.io 导出前关掉 Grid：`View → Grid` 取消勾选，或导出对话框里取消"Grid/Background"。⚠️ 上次实验2 的用例图导出时带了网格底纹，这次注意。
2. **字号**：工具里用 12–14pt（标题 16–18pt）；导出 PNG 宽度 **≥ 1500px**，缩到 A4 正文宽（约 15cm）后文字仍要看得清。
3. **配色低饱和**，只用一套色：界面层淡蓝 `#EAF1FB`／应用层淡绿 `#E8F5E9`／领域层淡黄 `#FFF8E1`／适配层淡紫 `#F3E5F5`／AI 能力淡蓝 `#E3F2FD`／数据淡青 `#E0F2F1`／执行淡橙红 `#FBE9E7`／人工确认淡橙 `#FFF3E0`；描边用同色系深色。
4. **红色 `#D32F2F` 只用于"禁止／异常／红线"**（真值隔离、重试上限、绕过护栏），不要拿来当普通线条色。
5. **框里只写短语**（≤ 12 字），整句话解释放图注或图下方说明区，避免框被文字撑破。
6. 导出后自己扫一眼：**有没有文字压线、框被撑破、箭头方向反了**。这三样是最容易被扣分的。

## 三、逐张规格

### 图 1　AI 与普通程序的职责边界图
- **文件**：`图1-AI与程序职责边界.png`　**放**：报告 3.1.3
- **画什么**：上方三栏等宽圆角框 —
  ① 左栏"交给 LLM（视觉语言模型）"：理解画面局面／生成候选动作与依据／判断"画面不可辨"并弃权／串成复盘叙述；
  ② 中栏"必须由规则程序完成"：截屏与画面有效性判定／动作合法性校验（护栏）／重试与失败恢复（≤2 次）／记录统计与档位控制；
  ③ 右栏"必须由人确认"：首次确认截图区域／同一动作连续 2 次未生效／模型与规则冲突／切入自动模式前。
  下方一条横向流水线 6 个方框：**屏幕像素 → LLM 理解与建议 → 规则护栏校验 → 玩家确认或执行 → 逐决策点记录 → 复盘报告**，框间画实线箭头。
- **怎么摆**：三栏等高；流水线在下方一行；从"LLM 理解与建议"绕过"规则护栏校验"直接连到"玩家确认或执行"画一条**红色虚线并在线上打红叉**，标"禁止：不得绕过护栏"；再用**橙色虚线**从"玩家确认或执行"引到右栏，标"异常／低置信／冲突 → 暂停并请求人工确认"。
- **注意**：底栏或图下加一句结论——"判断权归模型，放行权归规则，最终决定权归玩家"。

### 图 3　总体架构图（分层 + 调用方向）
- **文件**：`图3-总体架构图.png`　**放**：报告 3.3.2
- **画什么**：四条横向层带，自下而上被调用、自上而下依赖 ——
  ① **界面层 ui**：首页／入口、设置页（区域与档位）、核心任务页（建议卡）、复盘报告页、评测页（开发者）；

  ③ **领域层 core**：领域数据模型、提示强度策略、请求组装与响应解析、规则护栏、结构化记忆、端口协议（4 个 Protocol）；

  最下方一行"外部系统（不属于本软件）"：游戏窗口、云端 VLM 服务、本地文件系统、游戏真值通道。

- **注意**：图下写清主数据流一行——"界面层下发开始 → 应用层编排 → 适配层截屏 → AI 能力出建议 → 领域层护栏校验 → 适配层记录 → 复盘报告回界面展示"。

### 图 5　核心数据模型（类图）
- **文件**：`图5-核心数据模型.png`　**放**：报告 3.4.1
- **画什么**：7 个类。`DecisionPoint` 是**核心实体**，放中间；上排 `EvalResult`、`Run`、`Report`；下排 `Screenshot`、`Action`（值对象）、`MemoryItem`。
  字段只写关键的 4—8 个，并标 PK/FK，例如：
  `Run`：run_id(PK)、game_title、seed、started_at／ended_at、status、config_snapshot、outcome；
  `DecisionPoint`：dp_id(PK)、run_id(FK)、turn、seq、shot_id(FK)、state_summary、legal_actions[]、suggestion{action, reason}、confidence、player_action、is_consistent、model_meta{latency_ms, tokens, cost}、result{hp_delta, outcome}；
  `Screenshot`：shot_id(PK)、dp_id(FK)、path、width×height、sha256、region、is_valid；
  `Action`：action_type、card_name、target、energy_cost；
  `MemoryItem`：mem_id(PK)、state_signature、action、outcome、lesson、source_run_id(FK)、hit_count；
  `Report`：report_id(PK)、run_id(FK)、generated_at、path、key_points[]；
  `EvalResult`：eval_id(PK)、seed_set、baseline、n_runs、win_rate、avg_hp_loss、variance。
- **怎么摆**：`Run 1 —— 1..* DecisionPoint`、`DecisionPoint 1 —— 1 Screenshot`、`DecisionPoint 1 —— 1..* Action`、`DecisionPoint 0..* —— 0..1 MemoryItem`（虚线，表示"引用历史记忆"）、`Run 1 —— 0..1 Report`、`EvalResult 1 —— 0..* Run`；每条关系线两端**标重数**。
- **注意**：图下写明保存位置与敏感数据——"全部落盘在 `runs/<run_id>/`（screenshots、decisions.jsonl、report.md、memory.jsonl）；截图只覆盖游戏窗口区域；API 密钥只从环境变量读取，不进入任何数据实体"。

### 图 6　核心流程顺序图
- **文件**：`图6-核心流程顺序图.png`　**放**：报告 3.4.3
- **画什么**：8 条生命线：**玩家 ｜ 界面层 ui ｜ 应用层 app ｜ 截屏适配器 capture ｜ AI 能力 VLM ｜ 领域层护栏 core ｜ 执行器 exec(DryRun) ｜ 数据层 data**。
  消息按顺序编号（①—⑮）：① 开始／继续对局（档位＝仅复盘）→ ② 截取游戏窗口区域 → ③ 画面有效性判定（自调用）→ ④ 截图 PNG → ⑤ 决策请求（截图 + 通用动作 schema，不含任何游戏真值）→ ⑥ 解析为 JSON（空返回重试 1 次，自调用）→ ⑦ {动作, 依据, 置信度} → ⑧ 合法性校验 → ⑨ allow／deny + 原因 → ⑩ 记录决策点 → ⑪ 应用动作（默认 DryRun，不注入输入）→ ⑫ ok／injection_failure → ⑬ 更新建议卡与状态条（时延、费用）→ ⑭ 战斗结束生成复盘报告 → ⑮ 报告路径回界面展示。
- **怎么摆**：三条**红色虚线**异常分支，分别从 VLM、护栏、执行器指向 app：低置信／无法识别 → 暂停并请求人工确认；冲突 → 以规则为准；连续 2 次未生效 → 停止执行。异常分支的 y 位置要**留足以免标签互相压住**（每条异常与相邻正常消息至少间隔 40px 左右）。
- **注意**：自调用画成小方框回环；图下用一行"约定"说明蓝＝正常、红虚线＝异常，且三条异常都先落盘再提示。

### 图 7　失败恢复状态图
- **文件**：`图7-失败恢复状态图.png`　**放**：报告 3.4.4
- **画什么**：10 个状态 —— 主链：`空闲 Idle → 采集中 Capturing → 决策中 Deciding → 校验中 Guarding → 执行中 Applying → 记录中 Recording → 本局完成 Done`；异常链：`等待人工确认 WaitingHuman`、`已暂停 Paused`、`已终止 Aborted`。
- **怎么摆**：主链横向排一行，异常状态排第二行；迁移标注写成"事件／动作"，例如 Capturing--画面有效-->Deciding、Guarding--allow-->Applying、Recording--已落盘-->Capturing（循环）、Deciding--无法识别／空返回（重试 1 次后）-->WaitingHuman、Guarding--冲突（以规则为准）-->WaitingHuman、Applying--连续 2 次未生效-->WaitingHuman、WaitingHuman--失败达上限／人工选择终止-->Aborted、任意状态--玩家暂停-->Paused、Paused--恢复-->Capturing、Aborted--人工处理后-->Capturing、Done--生成复盘报告-->Idle。
- **怎么摆（线型）**：实线＝正常流转；**橙色虚线**＝异常转入等待人工确认；灰色虚线＝玩家主动暂停；**红色虚线**＝终止与恢复；蓝色虚线＝循环与恢复。
- **注意**：图下列三行硬约束——模型超时／空返回重试 1 次、动作注入未生效重试不超过 2 次、达上限后停止自动执行（对应验收 A4）；护栏冲突以规则为准（A5）；画面不可辨不猜测（A3）。

### 1. 图 5　核心数据模型（Class Diagram）

**第 2 步｜加属性与方法**：选中类 → 右侧 **Property** 面板 `Attributes` 一栏点 `+` 加属性、`Operations` 一栏点 `+` 加方法（右键类框 `Add → Attribute / Operation` 等效）。填写规则：

- **属性**：`Name` 填字段名（主键/外键直接写在名字里，如 `dp_id（PK）`），`Type` 填类型（`str`／`int`／`float`／`bool`／`datetime`／`list[Action]`／`dict`）。

### 2. 图 6　核心流程顺序图（Sequence Diagram）

**第 2 步｜画 15 条正常消息**（Toolbox `Message`，从发送方生命线拖到接收方生命线）。
✅ 实际导出时已把消息统一编号为 **1—18**（16／17／18 是三条异常分支），报告图注按这个编号撰写，图不必再改。

```
① 开始／继续对局（档位＝仅复盘）        ui   → app
② 截取游戏窗口区域                     app  → capture
③ 画面有效性判定：非黑屏、尺寸正常      capture → capture（自调用）
④ 截图 PNG（含 sha256）                capture → app
⑤ 决策请求：截图 + 通用动作 schema      app  → VLM   （不含任何游戏真值）
⑥ 解析为结构化 JSON；空返回重试 1 次    VLM  → VLM   （自调用）
⑦ {动作, 依据, 置信度}                 VLM  → app
⑧ 合法性校验（动作 ∈ legal_actions）    app  → core
⑨ allow / deny + 原因                 core → app
⑩ 记录决策点（JSONL + 截图归档）        app  → data
⑪ 应用动作（默认 DryRun：不注入输入）    app  → exec
⑫ ok / injection_failure              exec → app
⑬ 更新建议卡与状态条（时延、费用）       app  → ui
⑭ 战斗结束：生成逐回合复盘报告          app  → data
⑮ 报告路径 → 界面展示复盘              data → ui
```

冲突 → 以规则为准，记录 guardrail_trigger                     core → app

报告图注写的是"红色＝异常路径"（不写"虚线"），不用返工。

**第 4 步｜垂直间距**：拖动消息线调 y 坐标，确保每条消息的文字标签与上下相邻消息至少间隔 20px，
