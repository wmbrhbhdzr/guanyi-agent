# 实验5 AI 辅助编码协作记录

> 对应讲义 2.6：记录 AI 生成或修改代码的任务、关键输入、AI 建议、采用/拒绝、人工修改与测试验证；
> 并检查不存在的接口、无用依赖、遗漏的异常处理与明显安全问题，至少给出一条
> “AI 初稿—人工修正—测试通过”的完整证据。
>
> 实验5 的协作方式与实验4 相同：AI 负责按设计落地代码与文档，本人负责定范围（STS2 数据、小覆盖知识库）、
> 运行验证、核对回答是否符合游戏事实，以及“要不要改”的取舍。

## 一、五次“AI 初稿 → 运行暴露 → 人工修正 → 测试通过”

### 案例 1　接口地址多拼了一个斜杠（404）

- **任务**：写 `scripts/build_kb.py` 抓取 STS2 数据。
- **AI 初稿**：`url = "%s/%s" % (API, path)`，而传入的 `path` 已以 `/` 开头。
- **现象**：第一次运行直接 `HTTPError: 404`（实际请求成 `/api//characters`）。
- **修正**：改为 `"%s%s"`；随后 6 个接口全部取到数据。
- **验证**：`build_kb.py` 输出“卡牌 26、关键词 7、状态 11、敌人 4、遗物 5，合计 53 条”。
- **正确性说明**：URL 拼接必须约定“谁负责斜杠”，否则重复或缺失都会 404；这是低风险但高频的错误。

### 案例 2　**猜错数据 id** 导致知识库缺条目

- **任务**：按 STS1 的经验选择卡牌/敌人 id（`JAW_WORM`、`METALLICIZE` 等）。
- **现象**：首轮生成后“敌人 0 条、遗物 2 件、状态 8 条”，与预期不符。
- **关键输入（人工核对）**：打印接口原始数据的真实 id 与字段（STS2 的 id 是 `ASSASSIN_RUBY_RAIDER` 这类），
  发现 STS1 与 STS2 的卡池、敌人、状态 id 完全不同。
- **修正**：改为**从数据反推选择**——卡牌取“起始卡组 + 全部普通牌 + 3 张示例高级牌”；
  敌人从 `encounters[].act` 里筛 `Act 1`，按“普通/精英/首领”各取若干；状态与遗物按真实 id 白名单。
- **验证**：53 条片段生成成功，抽查确认中文名、数值、来源都正确。

### 案例 3　测试断言写错一个字

- **任务**：为 Prompt 模板写单元测试。
- **AI 初稿**：断言 `assertIn("只依据", system_prompt)`，而模板实际写的是“**只能**依据”。
- **现象**：`24 tests, 1 failure`。
- **关键输入（人工判断）**：对比模板正文后确认**断言错、实现对**，不改实现。
- **修正**：断言改为“只能依据”；复测 24/24 通过。

### 案例 4　超时被误分类成“网络不可达”

- **任务**：实现模型调用的失败处理（讲义 2.1 要求测连接失败/接口不可用/超时）。
- **AI 初稿**：只捕获 `HTTPError` 与 `URLError`，超时统一归入 `network_error`。
- **现象**：失败场景实测把 1 毫秒超时判成 `network_error`（应为 `timeout`）。
- **修正**：在 `URLError` 分支里判断 `isinstance(reason, TimeoutError)` 或包含 `timed out`，归类为 `timeout`。
- **验证**：复测三种失败分别得到 `http_401`、`network_error`、`timeout`，且鉴权类错误不重试、网络类错误按次数重试。

### 案例 5　**自动判定把错误答案判成正确**

- **任务**：写对照实验脚本 `scripts/run_qa_eval.py` 的自动检查。
- **AI 初稿**：期望要点用字符串包含判断（如 Q1 期望 `["10","3 层易伤","2"]`）。
- **现象**：
  1. 正确回答被判错（“伤害从 8 提升到 10……从 2 层提升到 3 层”没有字面的“3 层易伤”）；
  2. 反过来，**直接模型组把费用说成 1 费（实际 2 费）却被判正确**，因为“2”出现在“2 层”里。
- **关键输入（人工复核）**：逐条对照知识库数值人工判断，发现自动判定只能当粗筛。
- **修正**：期望要点改为“数值逐项出现”，并在报告里**并列自动判定与人工判定**两列，
  明确写出 Q1 直接组“自动✅、人工❌（费用错误）”。
- **结论**：自动检查适合发现“明显缺项”，**不能替代人工事实核对**——这条经验写进了报告结论。

## 二、代码审查（讲义 2.6 要求的四类检查）

| 检查项 | 方法 | 结论 |
| --- | --- | --- |
| 不存在的接口 | `importlib` 导入全部模块 + `compileall` | 通过；`guanyi/knowledge`、`guanyi/ai/llm_client`、`guanyi/app/qa_service` 相互引用正确 |
| 无用依赖 | 扫描 `guanyi/`、`tests/`、`scripts/` 的 import | 实验5 仍**只用标准库**（urllib／json／re／math／tkinter），未引入分词、向量、SDK 依赖 |
| 遗漏的异常处理 | 对照失败场景与 RAG 链路逐个检查 | 补齐：缺密钥／HTTP 错误／网络不可达／**超时**／空返回；资料不足时不调用模型；报告文件读取失败有中文提示 |
| 明显安全问题 | 检查密钥、外发内容、路径与日志 | 密钥只从 `.env` 读取且**不打印**、`.env` 已被忽略；知识库与请求**不含对局数据/截图/个人信息**；日志不写密钥 |

## 三、结论

1. 实验5 的代码问题集中在**数据接口契约**（URL、id、字段）与**判定口径**（超时分类、自动判定过粗），
   都属于“跑一次就暴露”的问题——说明先跑通再优化的顺序有效。
2. AI 可直接交付的部分：调用封装、Prompt 模板、检索打分、Markdown 渲染；
   必须人工把关的部分：**数据源选择与 id 映射、回答是否符合游戏事实、自动判定的可信度**。
3. 已知局限：分词与检索仍是轻量方案（词表 + 2-gram + BM25 + 词频余弦），未做嵌入向量；
   引用可靠性只做到“编号有效、片段可对应”，尚未逐句核验。
