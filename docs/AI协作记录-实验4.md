## 二、四次完整的“AI 初稿—人工修正—测试通过”

### 案例 1　Tkinter 在虚拟环境里起不来（环境适配）

- **任务**：为实验4 提供可运行界面（讲义 2.3 要求“输入页、列表/详情页”）。
- **AI 初稿**：`guanyi/ui/main_window.py` 直接 `import tkinter`，用 `python -m guanyi.ui` 启动。
- **现象**（跑冒烟测试时暴露）：
  `_tkinter.TclError: Can't find a usable init.tcl in the following directories: C:/Python/lib/tcl8.6 …`
- **关键输入（人工做的对照实验）**：
  - 系统解释器：`C:\Python\python.exe -c "import tkinter; tkinter.Tk()"` → **Tk OK 8.6**
  - 虚拟环境：同样代码 → 失败
  - 结论：**不是没装 Tk，而是 venv 找不到 Tcl 的库目录**（venv 的 `sys.prefix` 指向虚拟环境，
    而 Tcl 数据文件在基础解释器目录下）。
- **修正**：新增 `_ensure_tcl_env()`，在创建窗口前按需把 `TCL_LIBRARY`／`TK_LIBRARY` 指向
  **基础解释器**的 `tcl/tcl8.6`、`tk8.6` 目录。
- **测试验证**：`scripts/ui_smoke.py` 从“抛异常”变为三页全部跑通（新建对局 → 建议 → 记录两笔 → 列表 → 报告）。
- **关键代码为何正确**：`getattr(sys, "base_prefix", sys.prefix)` 在 venv 里指向基础解释器、
  在普通环境里等于 `sys.prefix`，两种情形都能拼出正确路径；只在变量未设置且目录存在时才写入，
  不会覆盖使用者自己配的环境变量。
- **局限**：目录名 `tcl8.6`／`tk8.6` 是写死的，升级 Tcl 版本需要跟着改；
  更稳的写法是遍历 `base/tcl/*` 取最高版本，或改由安装脚本写环境变量。

### 案例 2　AI 写的测试断言与实现不一致（业务语义）

- **任务**：为“规则基线决策”写单元测试。
- **AI 初稿**：断言“血量 42、敌人意图 11 → 应建议【防御】”。
- **现象**：`AssertionError: '打击' != '防御'`。
- **关键输入（人工判断）**：规则写的是“敌人意图 ≥ 当前血量的三分之一才保血”，
  42 ÷ 3 = 14 > 11，**实现是对的、断言是错的**——不能为了让测试变绿去改实现。
- **修正**：断言改为“打击”，并**补充用例 7b** 专门覆盖保血分支（血量 20、意图 11 → 防御）。
- **测试验证**：`unittest` 11/11 通过。
- **关键代码为何正确**：阈值比较写成 `intent * 3 >= max(1, hp)`，用乘法避免浮点误差，
  `max(1, hp)` 兜住血量为 0 的边界，不会出现“除以零”式的意外。
- **局限**：这只是**可解释的基线**，不代表最优打法；它的价值在于实验6 能拿它和模型对比，
  回答“模型是不是真的更好”，而不是充当标准答案。

### 案例 3　界面摘要与实际输入不一致（数据一致性）

- **任务**：核心任务页录入局面并记录决策点。
- **AI 初稿**：把“局面摘要”做成可编辑文本框，只在点击按钮时才生成。
- **现象**（人工截图核对时发现）：改了“敌人意图”却没有重新生成摘要，
  于是记录里摘要写“意图攻击 11”，而基线决策用的是 30 —— **同一条记录里出现两个真相**。
  用 `scripts/ui_smoke.py` 复现：列表第 2 行的摘要与决策输入不符。
- **关键输入（人工决定）**：摘要不允许自由编辑，应由结构化输入**自动生成**。
- **修正**：摘要框改只读；新增 `refresh_summary()`；绑定 `<KeyRelease>`／`<FocusOut>`／
  列表选择事件；启动、切换对局、记录成功后都自动刷新。
- **测试验证**：冒烟测试新增两条检查——“启动时摘要已生成”“改数字后摘要随之变化”，
  单测仍 11/11 通过。
- **关键代码为何正确**：唯一数据源是表单里的数字与手牌选择，摘要只是渲染结果，
  从结构上消除“两处不一致”的可能；`silent=True` 让输入过程中的半成品静默跳过，
  不会每按一个键就弹窗。
- **局限**：只读之后，玩家无法补一句自己的话；后续若确实需要，应新增独立的“备注”字段，
  而不是重新放开摘要。

### 案例 4　`.gitignore` 误忽略源码目录（仓库卫生）

- **任务**：把实验4 的代码提交进仓库，并让两个版本的 Tag 可被复现。
- **AI 初稿**：`.gitignore` 用 `data/`、`runs/` 忽略运行产物（实验1 时期写入的规则）。
- **现象**（从仓库视角核对时暴露）：
  - `git ls-tree -r exp4-v0.2-tested` 里 `guanyi/` 只有 17 个文件，**整个 `guanyi/data/`（数据访问层）缺失**；
  - `git check-ignore -v guanyi/data/store.py` 显示命中 `.gitignore:36: data/`；
  - 后果：两个 Tag 从干净克隆都跑不起来，而**本地一直正常**——因为被忽略的文件始终留在磁盘上。
- **关键输入（人工核对）**：用 `git ls-tree`（提交里到底有什么）、`git check-ignore -v`（哪条规则命中）、
  `git show <tag>:path`（历史版本内容）三条命令逐项验证，而不是只跑 `git status`
  ——`git status` 对“被忽略的文件”是沉默的。
- **修正**：
  1. `.gitignore` 改为根锚定：`/data/`、`/runs/`、`/logs/` 等；
  2. 补提交 `guanyi/data/{__init__,store,reporter,sample}.py`（commit `60afacc`）；
  3. 重建两个 Tag 指向修复后的提交，并剔除误入的 `__pycache__/*.pyc`；
  4. 在仓库外的临时工作树里实际检出 `exp4-v0.1-initial` 跑一遍，确认初版可运行。
- **测试验证**：`unittest` 11/11；`git ls-tree` 显示两个 Tag 均含数据层；
  初版工作树里 `python -m guanyi.cli list` 正常，`show --run run-9999` 复现初版的裸异常栈。
- **关键代码为何正确**：以 `/` 开头的忽略规则只匹配**仓库根目录**下的同名目录，
  因此 `data/runs/`（运行数据）仍被忽略，而 `guanyi/data/`（源码）不再受影响。
- **局限**：忽略规则的副作用只能靠“提交后从仓库视角检查”发现；更稳妥的做法是提交前
  用 `git ls-tree` 或 CI 核对关键源码目录是否齐全，而不是依赖“本地能跑”。

## 三、代码审查（讲义 2.6 要求的四类检查）

| 检查项 | 检查方法 | 结果 |
| --- | --- | --- |
| **不存在的接口** | 导入全部 13 个模块 + `compileall guanyi scripts tests` | 全部通过，没有失效引用（`guanyi/ui/main_window.py:42-45` 等导入均指向真实模块） |
| **无用依赖** | 扫描 `guanyi/`、`tests/`、`scripts/` 的 import 语句 | 实验4 代码**只用标准库**（json／pathlib／dataclasses／logging／tkinter／argparse／uuid）；`requirements.txt` 里的 requests／mss／pyautogui／dotenv 是实验1 探针与后续实验使用，实验4 未用到——保留不动，避免破坏已交付的实验1 环境 |
| **遗漏的异常处理** | 对照初版 6 个失败用例，逐个检查 `open()`、`json.loads()`、`int()` 调用点 | 发现并修复 6 处：① 文件不存在 → `NotFoundError`；② JSON 损坏 → 逐行容错 + 行号报告；③ 重复录入 → `DuplicateError`；④ 取值越界 → `ValidationError`；⑤ 枚举非法 → `ValidationError`；⑥ **`on_report()` 里 `open(...).read()` 未关闭句柄 → 改为 `Path.read_text()`** |

## 四、结论与已知局限

1. **四次修正都由“运行/核对”暴露**，不是靠读代码猜出来的——先跑测试与冒烟脚本，再改代码，
   能避免“把实现改成迎合错误预期”。
2. **可以放心交给 AI 的部分**：领域数据模型、JSONL 读写、报告生成、CLI 骨架、测试脚手架。
   **必须人工把关的部分**：环境适配（Tcl 路径）、业务语义（保血阈值这类规则取值）、
   数据一致性（一处真相）、异常边界。
3. **已知局限**：规则基线只是基线；界面仅覆盖核心流程（首页/设置/评测页仍是草图）；
   未考虑并发与多用户（本地单用户工具）；`data/runs/` 的清理策略尚未实现。
